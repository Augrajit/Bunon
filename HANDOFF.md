# HANDOFF: how to continue Bunon without the original assistant

Written 26 Nov 2026 on branch `v2`. Read this together with `CLAUDE.md` (rules and commands), `PLAN_V2.md` (the approved plan; its decisions block wins) and `SPEC.md` (dated decision log, D1–D14 and later).

**State in one paragraph.** `main` (the live app, https://buunon.streamlit.app/) still runs the pre-PLAN_V2 demo. `v2` holds D12 (success = good pieces after QC within a tolerance), D13 (order store, service layer, the app around one order's timeline) and D14 (the thin loop end to end: sourcing → offers → split → update → forecast → rescue → QC → track record). All of it replays offline from the LLM cache. Merge `v2` into `main` only when the product owner approves.

## 1. The rules (never break these)

1. **The LLM never produces a number.** Enforced in code:
   - *Reading text* (`agent.parse_order`, `parse_reply`, `parse_update`, `parse_news`, `steer`): every value comes with `source_span`, a verbatim quote. `textnum.contains(text, span)` must find the quote, and `textnum.states_number(span, value)` / `states_date(span, value)` must confirm the quote states that value. Otherwise the value becomes `None` with status `rejected` or `missing`, and a human enters it.
   - *Writing text* (`agent.write_memo`, `analyst.answer`): the LLM may write no digits and no number words. It may use only `{{key}}` placeholders from a `FactSheet` (numbers computed by the engine) and `{{fac:F0123}}` for factories. `agent.check_text` rejects violations; then one retry; then a deterministic template.
   - *Decisions* the LLM suggests (accept/reject/counter, status) are settled by code (`validate_reply`: a "yes" with a lower verified quantity or a delay becomes "counter"; zero pieces becomes "reject").
   - News severity is a label only; its effect is the fixed `SEVERITY_TABLE` in `config.py`.
2. **Approvals.** Nothing is ever sent to a factory automatically. Every plan, split, rescue and outgoing message needs a click by an exporter role (`service._require_exporter`). "Sent" means "shown in the factory's in-app inbox". Only the Quality inspector records QC. Roles are recorded, never names.
3. **Offline demo.** `BUNON_LLM_MODE=offline` (default) reads only `data/llm_cache/`; a miss raises `CacheMiss` and the caller falls back to a template or hand entry, never an error. The cache key covers the provider, model, task, prompt version and the **exact prompt text**. So changing any of these invalidates cached answers: a prompt string, a `*_VERSION`, a demo input, persona text, or **anything that changes engine numbers** (they appear in memo and analyst prompts). After such a change:
   ```
   set BUNON_LLM_MODE=live   (needs GEMINI_API_KEY in .env; never print or commit it)
   .venv/Scripts/python.exe -m bunon.warm_cache
   ```
   Then walk the whole app once in live mode (the loop's offer/update/rescue parses are also warmed by `warm_cache`). Then switch back to offline and run `pytest -m sweep`: it fails if the intake answer is not cached. Live calls are capped: 40 per visitor session and 400 per day.
4. **Pseudonymisation (public repo).** Factories appear only as `F0001`–`F3196`, with coordinates rounded to 2 decimals and workers rounded to 50. Never commit or send to the LLM factory names, `os_id`, addresses, `data/raw/` (raw CSV) or `data/private/` (the ID mapping); both directories are gitignored. `agent.assert_pseudonymous` checks every prompt; `tests/test_data_gen.py` scans every DB cell.
5. **Synthetic is labelled.** All capacity, price and history data is synthetic (seed 42) and labelled "synthetic" in the UI. Personas are **hand-written by the team**, labelled simulated, and never generated by the LLM. Values marked `ASSUMPTION` / `PLACEHOLDER` in `config.py` wait for research (`RESEARCH_ASKS.md`); never tune them to improve results.
6. **Working method.** Work on `v2`. Commit after every working step with tests green and push to `v2`. Record each design change in `SPEC.md` with its reason and before/after numbers. Update `PROMPTS.md` when a prompt changes. Run `pytest -q` and `pytest -m sweep` before committing a UI change. At each milestone, an independent reviewer (a person, or a fresh AI session) checks it against SPEC.md, rule 1, rule 2 and rule 3 before work continues.

## 2. Running it locally (Windows, Python 3.11)

```
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements-dev.txt
.venv/Scripts/python.exe -m streamlit run app.py            # http://localhost:8501
.venv/Scripts/python.exe -m pytest -q                        # ~170 unit tests, ~1 min; 5 skips on a clean clone are normal
.venv/Scripts/python.exe -m pytest tests/test_loop.py -q     # one file
.venv/Scripts/python.exe -m pytest -m sweep -q               # app click-through at 24 extreme settings, ~5 min, offline
.venv/Scripts/python.exe -m bunon.personas                   # validate data/demo/personas.json
```

The login page has a "Continue as demo exporter" button; nothing typed there is checked or stored. In the sidebar, pick a role. To walk the loop: confirm the order → approve the plan → approve and send the sourcing round → "Go to day 2" → approve the split → "Go to day 12" → choose a rescue → approve, send → "Go to day 26" → switch the role to Quality inspector → Record QC → the track record appears.

## 3. What is built, file by file

### Engine (no LLM)
| File | What it does |
|---|---|
| `bunon/config.py` | Every constant and assumption: dates (`AS_OF` = 3 Jan 2027 = story day 0, `DATA_AS_OF` = 20 Nov 2026), tolerance 2%, QC days, CM 60 BDT and material 76.5 BDT (placeholders derived in DATA_PROVENANCE §6.1), defect and lot-rejection placeholders, `SEVERITY_TABLE`, LLM caps. |
| `bunon/schemas.py` | Pydantic contracts: `OrderConstraints`, `OptimizerParams`, `Candidate`, `AllocationPlan`, `BufferPoint`, `PlanResult`, `ReplanResult`, `ReliabilityForecast`, `ShockEvent`, etc. |
| `bunon/data_gen.py` | Builds `data/processed/bunon.db` from the private raw CSV: pseudonymous factories plus seeded synthetic job history (with QC columns). Needs `data/raw/factories.csv` (local only). |
| `bunon/reliability.py` | Empirical-Bayes forecast per factory (`eb-3`): on-time probability, delay distribution, capacity factor, defect rate and lot rejection. `fit(history, ids)`. |
| `bunon/simulation.py` | Monte Carlo `simulate(plan, forecasts, slack, ...)` → P(good pieces after QC by the deadline ≥ (1 − tol) × Q), seeded. |
| `bunon/optimizer.py` | `load_world`, `demo_order`, `build_candidates`, `solve_mip` (PuLP/CBC), `solve_baseline` (naive), `search_buffer`, `compare_three`, `baseline_to_match`, re-plans (`replan_exclude`, `replan_locked`, `replan_from_reply`), news events (`event_from_severity`, `adjust_for_events`, `search_with_events`, `assess_news`). |
| `bunon/loop.py` | The order loop's engine steps: `sourcing_list`, `draft_request` / `draft_rescue_request` (templates), `OfferTerms`, `split_from_offers`, `Forecast`, `forecast_after_update`, `last_rescue_day`, `RescueOption`, `rescue_move`, `rescue_options`. Constants `REPLY_DAY=2`, `UPDATE_DAY=12`, `QC_DAY=26`. |

### LLM layer
| File | What it does |
|---|---|
| `bunon/llm.py` | The only file that imports `google-genai` (model `gemini-3.5-flash-lite`). `LLMClient.complete_json(task, version, prompt, schema)` with the disk cache, modes, `CacheMiss`, `BudgetExceeded`; a tool session for the analyst. |
| `bunon/textnum.py` | Number and date checks for quotes: lakh grouping, `150k`, crore, Bangla digits, Banglish number words, day-first dates. `contains`, `numbers_in`, `states_number`, `dates_in`, `states_date`, `literal_numbers`. |
| `bunon/agent.py` | Intake (`parse_order`, `intake_v*`), decision memo (`FactSheet`, `factsheet_for_plan`, `write_memo`, `check_text`, `template_memo`), factory replies (`parse_reply`, `reply_v1`), daily updates (`parse_update`, `update_v1`), news (`parse_news`), steering (`steer`), `assert_pseudonymous`. |
| `bunon/analyst.py` | "Ask Bunon" what-if loop: the LLM calls `run_simulation`, `solve_plan`, `compare_plans` (max 6 calls, logged), then answers with placeholders only. |
| `bunon/warm_cache.py` | Fills the cache for every scripted step (needs live mode and the key). |

### State and service
| File | What it does |
|---|---|
| `bunon/store.py` | SQLite per visitor session (`data/runtime/sessions/<32-hex>.db`). Column-checked `insert`, `rows`, `update_messages`. `cleanup_sessions(24h)`. |

Role checks live here. |
| `bunon/decisions.py` | Legacy approval log (`BUNON_DECISIONS_DB`) and the draft purchase-order text. |
| `bunon/personas.py` + `data/demo/personas.json` | Persona fixture: six simulated factories (F1856, F1064, F2184, F0824, F0288, F2829) and the scripted QC shares. Every message is currently `placeholder: true` (developer's stand-in). How to swap in the team's text: `data/demo/PERSONAS_GUIDE.md`. |
| `bunon/checkpoint.py` | Regenerates `CHECKPOINT_DAY2.md` (old milestone report). |

### UI
`app.py` renders only. Login gate → welcome → role switcher → three views: **Order timeline** (`view_timeline`: intake, plan + memo + approval, then `section_sourcing`, `section_offers`, `section_split`, `section_update`, `section_rescue`, `section_qc`, `section_record`, then "Ask Bunon" and the event timeline), **Show the maths** (`view_maths`), **Factory app** (`view_factory`, phone frame). LLM steps are memoised per session with `llm_once`. Look and feel: `.streamlit/config.toml` plus the single `THEME_CSS` block. **Hosting quirk:** Streamlit Cloud keeps imported modules, so `app.py` hashes `bunon/*.py` and reloads a fixed list of modules; any new `bunon` module **must be added to that list** (a test in `tests/test_service.py` checks this).

### Tests (`tests/`)
`test_engine.py` (optimizer, re-plans), `test_quality.py` (QC model), `test_agent.py` (quote rules, placeholder rule), `test_analyst.py`, `test_budget.py`, `test_data_gen.py` (privacy scan), `test_personas.py`, `test_service.py` (store, roles, cleanup, reload list), `test_loop.py` (the loop), `test_app_sweep.py` (`-m sweep`, Streamlit AppTest click-through at 24 settings).

## 4. Known issues and open questions

Known issues:
1. F2829's standby reply ("Rate 60 BDT per piece") is parsed as **counter**; the answer key says accept. A rate stated in answer to "your rate" is not a counter. Harmless for capacity (counter and accept are treated alike); fix in the offer parser (task 2.3).
2. Prices in replies are read only as quoted free text conditions, never as numbers.
3. Request drafts, rescue drafts and the warning text are fixed templates, not LLM-written.
4. `last_rescue_day` may name a factory that was never asked ("until when could anyone still make this", not "who will").
5. The planner's capacity windows start on day 0, slightly optimistic against production starting on day 2.
6. Only one scripted update per order; the forecast handles one late factory at a time.
7. The best plan reaches 87.5%, below the 90% target, mainly because of the lot-rejection placeholder (2%). That is honest, not a bug; do not tune it.
8. Persona text is all placeholder until the team delivers `personas.json`; any change needs a cache re-warm (rule 3).

Open questions for the product owner:
- Gemini tier of the current key (AI Studio); paid tier needed for any real-user test with real messages.
- Final submission deadline (assumed about 24 Dec; live final 26 Dec).
- Research asks 11–16 in `RESEARCH_ASKS.md` (whole-lot rejection frequency first; the T-shirt share of a set's sewing price checks the 40% assumption).

## 5. Remaining milestones as task lists

Conventions for every task: engine code stays free of LLM calls and Streamlit; `OrderBook` methods check roles, write an event with the acting role, and are idempotent (re-running a Streamlit rerun must not duplicate rows); row ids are scoped as `f"{order_id}:..."`; any new `bunon` module goes into `app.py`'s reload list. After each task: `pytest -q`, commit, push to `v2`. At the end of a milestone: `pytest -m sweep`, update SPEC.md, README numbers if changed, reviewer.

### Milestone 1: thin loop (D14, done) — leftovers
1.1 **Exporter payment record** (PLAN_V2 cut b). *Built after this handoff was written if SPEC.md D15 exists; check there first.*
   - `service.OrderBook.record_payment(order_id, factory_id, amount_bdt, due_day, paid_day, role)`: exporter roles only; `paid_day ≥ 0`; idempotent per factory; event `payment_recorded`.
   - `OrderBook.exporter_record(order_id) -> dict`: `{"payments": n, "on_time": k, "on_time_rate": k/n or None, "avg_days_late": float or None}`, computed only from the `payments` table.
   - Amount due per factory = approved allocation qty × the line's unit price (code, `due_day` = QC day + a payment term in `config.py`, marked PLACEHOLDER).
   - UI: `section_payments(oid)` after QC; table + "Record payment" per factory.
   - Tests: only exporter roles; on-time rate recomputes exactly; idempotent.
1.2 **Repeated causes, counted by code** (PLAN_V2 §0 item 2): `track_record` gains `updates_without_cause` (count of updates whose cause did not pass the quote check) and `cause_repeats` (same cause text more than once). UI wording: "no specific cause given", never "excuse". Test: two updates with the same cause → repeats = 1.

### Milestone 2: factory side (PLAN_V2 schedule 5–9 Dec)
2.1 **Factory answers a request in the phone view.** `view_factory`: for each sent request without an inbound reply, buttons Accept / Decline and a form "pieces I can make" + "days late" + free text. `OrderBook.factory_reply(order_id, factory_id, decision, qty, delay_days, text, role)`: factory roles only (`FACTORY_ROLES`), writes an inbound message (`kind="offer_reply"`, `is_simulated=0`, source `platform`) **and** an offer row directly (numbers typed by the factory are the factory's own statement, so no LLM is involved). Test: exporter role refused; offer row matches the form.
2.2 **Factory daily update form.** Same view: "pieces finished so far", "days late (0 if on time)", "reason" (free text). `OrderBook.factory_update(order_id, factory_id, pieces_done, delay_days, cause_text, role)` → `progress_updates` row and event `progress_update_received`; the exporter's `section_update` uses the latest update per factory (not only the scripted one). Test: exporter role refused; forecast uses the new update.
2.3 **Offer parser with price and ship date** (`reply_v2`).
   - `agent.ReplyLLM` gains `price_bdt_per_piece: FloatField`, `ship_date: DateField`; `REPLY_VERSION = "reply_v2"`; prompt adds both with the same "copy the exact words" rule.
   - `validate_reply(reply, out, planned_qty, asked_price=None)`: price must be quoted and stated (`states_number`); ship date via `states_date`; a price far outside `config.PRICE_RANGE_BDT` (new, PLACEHOLDER) is flagged in notes, not dropped. **Decision rule fix:** a stated price ≤ `asked_price` with no lower quantity and no delay is *accept*, not counter; a price above it is *counter*.
   - `service.record_offer` stores `price_bdt_per_piece`, `ship_date`; `loop.OfferTerms` gains `price`; `split_from_offers` uses the offered price instead of the candidate's synthetic price when present.
   - Tests in English, Banglish and Bangla for each field (persona `expected` answer keys); F2829's reply → accept; F2184 → counter on price.
   - Then re-warm the cache (rule 3) and update PROMPTS.md (A2 reply_v2).
2.4 **LLM-written request drafts** (`agent.write_request`, task `request_v1`): input a `FactSheet` with `{{qty}}`, `{{finish_by}}`, `{{gsm}}`, the factory as `{{fac:F…}}` and the language; output text with placeholders only; `check_text` → one retry → `loop.draft_request` template. Test: a draft with a digit is rejected and falls back; rendered drafts contain exactly the plan's numbers.
2.5 **Persona swap.** When the team delivers text: replace messages in `data/demo/personas.json`, set `placeholder: false`, run `python -m bunon.personas` (checks every expected number is written in the text), re-warm, adjust `loop.UPDATE_DAY` only if their update is on another day, record in SPEC.md.
Check it works: open the Factory app view at phone width (`resize_window` mobile, or a narrow browser), answer a request as Factory owner, see it in the exporter's offers table.

### Milestone 3: follow-up, warning, rescue (10–16 Dec)
3.1 **Several updates per factory.** `loop.forecast_after_update` already takes one `(factory_id, pieces_done, delay_days, day)`; add `loop.forecast_from_updates(world, b, point, cands, updates: list[dict], day) -> list[Forecast]` that applies the latest update per factory, all taken as certain together (extend `_certain` to a set of ids). Test: two late factories → shortfall is the sum; on-plan updates leave P unchanged.
3.2 **Warning module** (`loop.warning(fc, prev_p, target) -> Warning(severity, facts)`), severity from fixed thresholds in `config.py` (`WARN_DROP_PP`, PLACEHOLDER). 3.3 **Surge option** in `loop.rescue_options`: same factory adds overtime capacity `config.SURGE_SHARE` (PLACEHOLDER) at `config.SURGE_PRICE_FACTOR`; only if its projection plus surge covers the shortfall. Test: surge never exceeds capacity × (1 + share).
3.4 **LLM-written rescue drafts**, as 2.4 (`rescue_request_v1`).
3.5 Fix known issue 5: start capacity windows on `loop.REPLY_DAY` in `split_from_offers` (pass a start day into `build_candidates` or shrink `window_days`). Record before/after numbers in SPEC.md.

### Milestone 4: track record (10–16 Dec)
4.1 **Record across orders.** `OrderBook.factory_track_record(factory_id) -> dict` over all orders in the store: acceptance rate, on-time rate, QC pass rate, average reported delay, from `source='platform'` events/rows only; synthetic history shown separately (`service.factory_record`). Test: metrics recompute exactly from rows; simulated persona events are labelled.
4.2 **Delay attribution** (cut a, `agent.suggest_attribution`, task `attribution_v1`): input the update texts and recorded news events in the same district and days; output a category with a quote. **Code rule:** `outside_event` only if a matching recorded event id exists, else at most `unclear`. Human decides (exporter role); the factory can dispute (factory role) → `attributions` row. Tests for both branches.
4.3 **Factory controls sharing** (`share_settings`): factory role sets per-field visibility; the exporter view hides private fields. Test.

5.1 Demo fixture frozen: a test asserts the README/SPEC demo numbers (split 84.1%, projected 9,800, shortfall 3,300, P 81.8%, last rescue day 16, move 85.6% / +33,757 BDT) so script, README and video stay consistent. Update them whenever the engine or fixture changes.
5.2 Story-clock jump buttons for the 3-minute pitch (PLAN_V2 §7): "Day 2 replies", "Day 12 update", "Day 26 QC" each replays to that checkpoint.
5.3 Real-user test (one merchandiser, paid tier if real text, consent), notes in SPEC.md.
5.4 Docs pass (README, SPEC, PROMPTS, DATA_PROVENANCE), video under 181 s.
5.5 Release check: clean clone, `pytest -q`, `pytest -m sweep`, privacy scan, live timing; merge `v2` → `main` only with approval; tag.

## 6. Where to look when something breaks

- **Sweep says "timeline missing" or pydantic `model_type` errors:** a module is missing from `app.py`'s reload list.
- **Sweep fails at intake / memo shows the template:** cache miss; something in the prompt changed (rule 3).
- **Different numbers between runs:** look for unordered sets/dicts feeding the optimizer or a prompt; sort by `(-qty, id)` as the re-plan diff does.
- **A visitor sees another's data:** stores are per visitor session; check `store.session_db_path` and `BUNON_STORE_DIR`.
